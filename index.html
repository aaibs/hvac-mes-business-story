Chapter 0

The big picture — how an Australian ductwork shop makes money, and where MES sits

Industry context · CRM ↔ MES boundary · three locking gates

A ductwork shop in Australia sells three things: galvanised sheet metal cut, folded and assembled into ductwork to drawings (fabrication), bought-in materials that go with it (spiral, dampers, grilles — supply), and installation labour on site (install). A tenant may be supply-only (no install) or supply & install — per its capability profile. Money comes in from the builder/head contractor by tender package; money goes out on sheet metal (ordered by m², rolled up in kg), shop labour hours, install labour hours and transport. Margins are thin (GM in the low double digits — illustrative figure), so the whole game is: build exactly what was sold, build nothing extra, rework nothing, and be able to prove it to the client.

The system is split into two halves with a hard boundary. The front half is CRM (already built): email → lead → deal → tender package → estimating take-off → quote → win/loss decision per package. The back half is MES (111 features, currently a spec): from the moment a package is WON and the handover is ACCEPTED through to the work being installed and the margin calculated. Handover ACCEPTED is the point of no return: everything CRM finalised (scope, price, baseline take-off) becomes read-only for the shop.

MES is designed around three locking gates that nobody can bypass with personal privileges (gate 2 is absolute; gates 1 and 3 open only via an approved exception + audit through F69): (1) a drawing must be APPROVED_FOR_CONSTRUCTION before a production take-off can be done from it; (2) the production take-off must be LOCKED before work orders can be generated — and there is no unlock button; (3) QC checkpoints are blocking — a batch that has not PASSED does not move to the next operation. Plus one principle that runs throughout: never edit a record, only create a new one and supersede; snapshots are immutable; exceptions go through four-eyes approval; mobile runs offline-first.

Without the system

  • No hard boundary → the shop works from an estimate that is still being edited; sale price and cost are not on the same baseline.
  • No locking gates → sheet metal cut to an old drawing, a batch that failed QC keeps running, and by the time it is caught on site it is too late.
  • Editing in place instead of creating a new record → when the builder asks "why is this number different", nobody can trace it.
Outcome: All 111 features below are how MES runs the back half of the value chain within that framework.

Chapter 1

Winning the tender — turning a handover into a contract, a project and production packages

S1 · S2 · S3 · S4 — “Production setup” cluster

Three months ago, Alex took off and quoted the ductwork package for QEII Hospital Stage 2: 6,636 line items from CAMduct, priced at $1.05 million, split into three sub-packages — P1 Duct, P2 Pre-lag (pre-insulated duct), P3 Pre-join (pre-assembled) — across 13 zones (Level 01… Plantroom, Riser…). The builder chose Northbridge for P1 and P2 and dropped P3. CRM records two WON decisions, one NO_BID, and the deal becomes PARTIALLY_WON. On the shop side, Paul (Production Manager) reviews and clicks ACCEPT on the handover for each package — the acceptance screen must show the source quote + version, won_amount, zone and award_event group, so "sibling" handovers from the same round can be accepted in bulk.

That is the moment MES wakes up. From the first ACCEPTED handover, Sam/Jordan create the Contract (S1) — the system prefills contract_value from the package's won value, dates and scope; the user only adds the client contract number, payment terms and retention, then uploads the signed copy → SIGNED. This is the commercial baseline: the sale price of each package (won_amount taken from the quote package), scope and terms. A second handover on the same deal does not create a new contract but becomes a contract variation. Then Jordan opens the Production Project (S2) — the shop's workspace for this job; at this point the contract goes ACTIVE.

Jordan does not dump all 6,600 lines into one lump. He splits them into Production Packages (S3) by zone/level inherited from CRM — "L1 Supply", "L2 Return", "Plantroom", "Riser" — because each zone has a different delivery schedule (the builder wants Level 1 eight weeks earlier, Plantroom later). Then Paul assigns people (S4): Minh as detailer for L1–L3, Kate as planner for everything, Lee as QC owner. A package is only READY once it has assignments and a drawing set. Who is responsible for which package is clear from day one.

Without the system

  • No separate Contract → the sale price gets hand-edited in Excel, and later nobody knows the real margin against what was sold.
  • One job = one lump → Level 1 cannot be delivered early, nobody knows which package is running late, one person carries everything.
  • No assignments → every detailer "thought the other one was doing it", and the Level 2 drawings sit untouched for two weeks.

Chapter 2

Shop drawings — locking gate 1

S5 — Production Drawing Intake & Versioning

The tender drawings (used to quote) and the shop drawings (used to cut sheet metal) are not the same thing. The builder sends shop drawing Rev A for Level 1, a week later the consultant changes the riser dimensions → Rev B, then Rev C is the issued-for-construction version. The classic industry story: the shop cuts to Rev B while site installs to Rev C, and 40 fittings have to be remade.

MES takes shop drawings into a versioned Drawing Set / Drawing Version (S5). On each version Minh declares differs_from_tender + differences_note — what differs from the drawings at quote time — because that is a mandatory input to the variance review (S9). Only when a version has been reviewed internally (approver ≠ uploader) and marked APPROVED_FOR_CONSTRUCTION is it allowed to be the source for a production take-off. Old versions are not deleted — they are superseded, so that in a dispute Jordan can reopen exactly the version the shop cut to.

Without the system

  • Drawings sent by email/USB, everyone holding a different "latest" copy → cutting to the wrong revision is the most expensive mistake in the industry.
  • No approval status → the detailer takes off from a drawing not yet approved for construction, and the finished work has to be thrown away.

Chapter 3

Production take-off — from CAMduct, via API, into a snapshot, then LOCK

S6 · S7 · S8 · S9 · S10 — locking gate 2

Minh opens CAMduct (Autodesk Fabrication) and redraws Level 1 to Rev C as individual duct sections, fittings and dampers — each with its dimensions, sheet gauge, joint type (TDF/Pittsburgh) and insulation layer. This is the production take-off, distinct from the estimating take-off done at quote time: more detailed, based on the shop drawings, and it is what the shop will actually cut. Minh creates a Production Takeoff Run (S6, stage = PRODUCTION) tied to the approved drawing version.

Then Minh hits push in the CAMduct add-in. The data goes up to the MES via API (S7, source CAMDUCT_PLUGIN; if the plugin fails, FILE_UPLOAD MAJ/CSV) together with an export_manifest, becoming an import batch: RECEIVED → VALIDATING (map material/gauge via the camduct_mapping table shared with the CRM, check mandatory fields) → SNAPSHOTTED → ACTIVE. Nobody re-keys 1,200 lines. If Minh pushes a second time, the new batch fully replaces the old one (full-replace, not cumulative) — the old batch is kept for reconciliation.

Each line becomes an immutable Item / Part / Other Snapshot (S8), with per-batch roll-ups: qty, weight, metal area by gauge/material, insulation area by spec, labour units. The shop orders sheet metal by m² and costs labour by labour units, but weight is still one of the variance groups. Area has two concepts that must be kept separate: true area (for reconciliation) and est. metal area including waste% (the material allowance for F79/F58 — seam §21.1).

The step that matters most for money: Variance vs Handover Baseline (S9). The system places the production roll-up next to the baseline take-off that the CRM has pinned to the quote for this package (both sides of the numbers are supplied by the system, not keyed by hand). Level 1 is +6% on area because the consultant added two branches — Kate raises a variance_note for each difference, at level MINOR / MAJOR (PM confirms) / CRITICAL; CRITICAL makes a Production Change Request (F80) mandatory and Jordan raises a variation order in the VO register (§21.5) to submit to the builder before the shop cuts. Jordan signs off that the variance review is complete — that is the condition for the run to be APPROVED. This is where ductwork shops lose the most money: doing extra work that nobody knows to claim for.

Finally a reviewer (not the person who pushed) reviews, Paul (Production Manager, holding PRODUCTION_BASELINE_APPROVE) approves and then LOCKs (S10). From this second the production baseline is immutable, there is no unlock. Want to change it? Create a new run, supersede the old one, and the whole history stays intact.

Without the system

  • Re-keying the take-off from CAMduct into Excel → errors, 2 days lost per package, and nobody knows which Excel version is the final one.
  • No comparison against the baseline that was sold → silent scope creep: 6% extra work billed at the original amount.
  • No LOCK → the planner builds WOs on numbers that are still changing, and the shop floor cuts to yesterday's numbers.

Planning — work orders, batches, machine schedule, nesting, and QR labels

S11 · F16 · F79 · F91 · S12 · F14 · F75–F78

Kate looks at the LOCKED baseline for Level 1: 380 straight duct sections, 210 fittings, 40 pre-lagged sections. She groups them into Work Orders and Fabrication Batches (S11): the straight-duct batch runs on the coil line (continuous uncoil–cut–fold machine), the fitting batch runs on the plasma then across the assembly bench, and the pre-lag batch goes on to the insulation area. Each batch has a routing — a sequence of operations with QC checkpoints attached (F16).

When a WO is PLANNED, the system calculates material requirements and creates reservations (F79) by material × work order — for example 4.2 t of 0.8 mm coil for the coil-line WO, 1.1 t of 1.0 mm for the fitting WO (illustrative figures); if enough is available it goes RESERVED, if not, Kate sees the shortage to sort out with procurement. Allocation of specific lots/bins only happens at release or nesting. Then she places the batches on the Scheduling Board (F91): a finite-capacity schedule by machine and by labour/area (people capacity comes from the HRM). The coil line is booked out until Thursday → the Level 2 batch has to slip, the board warns immediately, rather than finding out on Friday morning.

Then QR labels (S12): Kate selects the print scope (WO / batch / piece) and the system generates labels for every job, every batch, every piece — printed and stuck onto the sheet metal (reprinting does not generate new codes). From now on everything on the floor is identified by scanning, not by marker pen. Kate releases the batch to the floor (F14) once the conditions are met — baseline LOCKED, routing complete, labels generated, reservation at the policy level — the work order goes RELEASED, the batch is QUEUED at the first op, a pick list is fired off to the store automatically (F41), and Dave sees the batch in his station's queue.

For the fitting batch, Nina (CAM engineer) creates a CAM job (F75) from the parts of the 210 fittings, runs nesting in CAMduct (nesting is allowed to run before release, per policy) and imports the result back into the MES; yield (F76) is a measured figure — sheet metal is 50–70% of material cost, and a 2–3% yield gain changes the package margin outright. The cut-file is dispatched to the plasma (F77) and the machine reports back QUEUED → DISPATCHED → CUTTING → CUT_COMPLETED (or FAILED). Leftover sheet after cutting is recorded as offcut/remnant (F78) and returned to the store — a good shop recovers 5–10% of material this way.

Without the system

  • Scheduling on a whiteboard → machine clashes found late, urgent batches jump regular ones, nobody knows what can be delivered this week.
  • No nesting/no yield measurement → sheet-metal scrap is a gut feeling; with sheet metal at 50–70% of material cost, a few % of yield is thousands of dollars per package.
  • No reservation → the store issues coil to another job, and the running batch runs out of sheet halfway through.
  • No QR labels → pieces cannot be traced: which job it belongs to, whether it has been done, where it is.

Quality — locking gate 3, and the paperwork that makes the builder accept the goods

F71 · F72 · F73 · F74 · F84 · F93

A hospital does not accept ductwork that "looks about right". The spec calls for pressure class and seal class to AS 4254.2, grease duct continuously welded to AS 1668 by welders holding AS/NZS 1554 tickets, and an ITP (Inspection & Test Plan) agreed with the builder before production (F84, DRAFT → AGREED). Lee — QC owner of the package, who also holds the QC Inspector role — configures QC checkpoints (F71) straight into the routing CUT → FOLD → SEAM → ASSEMBLE → SEAL → QC → PACK: one IN_PROCESS checkpoint checking dimensions after FOLD (before SEAM locks them in), and one FINAL checking seal/dimension/label after SEAL before PACK — flagged blocking.

When the Level 1 batch hits a checkpoint, the app opens a QC inspection (F72) for Lee (who must not be the person who just performed that op): measure, photograph, PASSED / PASSED_WITH_NOTE / FAILED; each PASSED automatically ticks the matching point in the ITP. A FAILED batch cannot move on — that is gate 3. Lee raises an NCR (F73) for 6 fittings with wrong dimensions, analyses the root cause, dispositions "rework" through exception approval (USE_AS_IS requires Production Manager approval), and places a quality hold (F74) on the whole batch until rework is done and re-inspection is PASSED; only once the hold is released can it go to packing.

At delivery, the builder demands a compliance pack: the completed ITP, inspection results and pressure-test cert, welder certificates, mill certs per sheet-metal lot, closed NCRs, and the POD. F84 collects all of it into one set per package (COLLECTING → ISSUED); a package cannot be DONE while the ITP is not COMPLETED. And when a dispute comes up three months later over a duct section on Level 2, material genealogy (F93) traces backwards: piece → batch → sheet → goods receipt → supplier → sheet-metal lot certificate.

Without the system

  • QC by eye + paper sign-off → defective batches still reach site; fixing on site costs 5 times as much as fixing in the shop.
  • No ITP/compliance pack ready → the builder holds the claim money until the paperwork is gathered, losing 2–3 weeks.
  • No material traceability → when a sheet-metal lot is defective, the whole job has to be recalled instead of just the pieces that used that lot.

In the office, Admin/Supervisor maintains the cage/pallet register (F28); Hoa (dispatch coordinator) watches the dispatch readiness dashboard (F29) — which packages are fully packed, have passed QC, and can go on the truck, and creates a dispatch load straight from there; supervisor/warehouse watch occupancy (F30): 14/20 cages IN_USE (illustrative), and a cage sitting on site for more than N days triggers a retrieval reminder.

Without the system

  • Packing without scanning → 3 fittings missing on site, the truck comes back; or 5 extra sections from another job.
  • No idea which cage holds what → unloading on site takes hours of hunting for items.
  • No occupancy tracking → run out of cages, finished goods sit on the floor waiting, taking up production space.

The builder does not accept deliveries at any time — each site has a delivery window set by the crane schedule and the site programme (for QEII, the commercial chain PO → DPA → approval → lead time per level sits on the CRM side; MES starts from the delivery window). Hoa (dispatch coordinator) creates a dispatch load (F31) and assigns the 9 PACKED cages for Level 1 to it → storage ALLOCATED, loading manifest printed. She then builds the transport route & schedule (F86): stops in sequence with distance/ETA and the site's time window, vehicle + driver (capacity check, no overlapping time slots), attaches the load to the schedule → the system generates a delivery trip and publishes the schedule to Tom on mobile.

On Tuesday morning, Tom scans the vehicle QR to check in (F87) — confirming the right vehicle, the right driver, and unlocking the loading step. He scans each cage onto the truck (F32) → storage LOADED; scanning a cage belonging to another load is hard-blocked; once 100% of lines are scanned the load is READY_DEPART (if short, the line is SHORT and Hoa decides whether to wait or split the load), then the driver/coordinator confirms DEPARTED (the loading scan itself is the point where responsibility passes from the shop to transport). On site, Tom reports ARRIVED, and Mick (site supervisor) and Tom scan the delivery (F33): delivery_stop DELIVERED with the receiver's identity + signature in the app or a confirmation photo → the POD (Proof of Delivery) is generated automatically and is immutable once the trip is COMPLETED. Site refuses delivery (damage, wrong item, site not ready)? REJECTED_AT_SITE with reason + photo, cage RETURNED for return/NCR handling. Back in the office, Jordan tracks ready → loaded → departed → delivered (F34) and answers the builder without having to call the driver.

The POD is not just a delivery confirmation. It is the evidence for claiming money against progress — each POD generates a claim_line UNCLAIMED, gathered into a progress claim at the period cutoff (F94, Chapter 10) — and it is the entry point to Site / Installation Management (F96): Jordan sets up install_task by package/zone from items that already have a POD, assigns a crew (SWMS/induction mandatory before starting); Mick has installers scan pieces → INSTALLED, records site defects with photos and a cause classification so they route correctly: fitting dented during unloading → TRANSPORT → transport claim; wrong dimensions → FAB → NCR back to the shop; missing → MISSING → re-plan dispatch. HSE on site — incidents, toolbox talks — links through to HRM.

Without the system

  • Delivery without POD → builder says "not received", the shop has nothing to argue with; claims hang for months.
  • No delivery schedule against the delivery window → truck arrives while the crane is busy, waits or turns back.
  • No defects recorded on site → fixed "by word of mouth", later becoming a dispute over who bears the cost.

Three months later a new coil lot comes in 6% higher, and the actual labour hours (from the scans in Chapter 5) for the Level 1 fitting batch are 15% above the quoted minutes. The critical question: how much does this job really make? And how should the next quote be priced correctly?

MES captures the unit price at the time of receipt (F53) — not the catalogue price — so the price history (F54), supplier comparison (F55), trends (F60) and analysis by period (F61) are all real numbers. Landed cost (F56) adds freight and charges to the sheet-metal price. Stock is valued by the chosen method (F57, default moving average — a new lot at a higher price updates the unit cost automatically); only an incorrect receipt price, late freight, a credit note from a claim or a change of method goes through an approved cost adjustment / revaluation (F62) — the original figures are never edited.

Each time Ravi issues sheet metal to a WO (F41), issue costing (F58) locks the unit cost at the time of issue per the material's costing method and traces it to the batch (F59). In parallel, labour costing (F70) takes Dave's reconciled labour_time_record multiplied by the labour_rate configured by skill level and shift (NORMAL / OT1 / OT2), effective by date, never retroactive; variance actual vs standard is shown by op/batch/worker. The two streams meet in the batch cost roll-up: Level 1 fitting batch = sheet metal + labour + scrap (NCR) + allocated overhead (optional) — OPEN while receiving cost, FINALIZED when the batch closes.

Then F81 — Job Cost Budget vs Actual / WIP / Profitability — puts it all next to the budget seeded from the quoting workbook (est. material budget, quoted minutes) and committed (reservations not yet issued + open POs): Level 1 budget $76,600, actual $71,900, 12% WIP remaining, forecast margin 29% instead of 32% (illustrative); revenue is computed on the revised contract value (original + Σ VO APPROVED). Jordan tracks budget/forecast; margin by package is a sensitive figure — Paul and Priya see it. Over the threshold, F82 warns before the job closes, not after. This is the Estimate ↔ Actual feedback loop: actual hours and real material unit prices are exported so estimating can adjust its rates next time. Money then flows two ways through F94: purchase costs — a completed PO match becomes a Bill in Xero; revenue — POD/install generates claim_line, at the period cutoff Jordan submits the progress claim, the client certifies, and only then does it become a Sales Invoice; Xero is the general ledger, MES does not post to the GL, and reads payment status back.

Without the system

  • Cost taken from the catalogue → phantom margin; a job "making 30%" turns out to make 12% when accounting closes the books.
  • No cost trace to the batch → no idea which batch lost money, or whether it was the sheet metal or the labour.
  • No Estimate↔Actual → Alex keeps quoting on old minutes while the shop spends more — or the reverse, losing tenders because the price is too high.
  • Re-keying into Xero by hand → errors, slow claims.

Chapter 13

Three systems joined — CRM, MES, HRM never enter anything twice

Seam · source of truth

The story above runs through three systems, and the principle is that every piece of data has one owner. CRM owns customers, deals, tender packages, quotes and handover — MES only reads (handover_snapshot, quote_version, won_amount, baseline take-off for variance comparison) and creates the contract / project / package itself from an ACCEPTED handover. MES owns labour hours (shift_session, operation_log → reconciled labour_time_record) — HRM pulls them for timesheets and payroll; per HRM_DOCUMENT, HRM does not allow manual hour entry. HRM owns people, certifications, rosters — MES reads certifications to gate the welding area (F2), reads aggregate capacity for the scheduling board (F91), but never sees personal leave reasons.

The two rates are two different things (seam MH-16, per HRM_DOCUMENT/briefing): the MES labour_rate is for cost; the HRM base_pay_rate (award/EBA) is for pay — plus 12% Super, casual loading, allowances, STP Phase 2 reporting with separate lines, pushed to Xero/MYOB/KeyPay via adapter. Changes travel two routes: before award a quote change request in CRM → a new quote version; after signing the VO register (§21.5, commercial) together with production change request F80 (technical), linked vo_id ↔ pcr_id — no shared object with CRM.

Without the system

  • Hours entered in two places → payroll and cost differ, and neither is right.
  • Mixing the pay rate with the cost rate → either workers are underpaid, or the job is costed at a loss.
  • Variations with no clear route → extra work done for free.
